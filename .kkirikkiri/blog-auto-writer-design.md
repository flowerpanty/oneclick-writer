## 1. 전체 아키텍처

### 1.1 시스템 개요

**방식: Claude Code 스킬 (Skill)** -- 에이전트 방식 불채택

스킬을 선택한 이유:
- 블로그 작성은 선형 파이프라인 (입력->리서치->스타일->생성->검토). 병렬/자율 판단 불필요
- `/blog-writer 주제` 한 줄로 시작하는 UX가 최적
- 기존 SKILL.md 구조가 이미 존재하므로 점진적 개선이 합리적
- 에이전트는 스폰 오버헤드, 상태 관리 복잡성, 사용자 학습 비용이 큼

유일한 에이전트 활용: 리서치 단계에서 Agent 도구를 서브에이전트로 호출하여 메인 컨텍스트 윈도우를 보호

### 1.3 네이버 블로그 수집 전략 (계층적 폴백)

네이버 블로그는 iframe 기반 렌더링 구조로 단순 HTTP fetch로 본문 접근 불가.
기존 서버 코드(server.js)에서도 Naver Search API의 snippets만 사용하고 본문 fetch는 시도하지 않음.

**폴백 순서:**

| 순서 | 방법 | 설명 |
|------|------|------|
| 1 | WebFetch 직접 시도 | 원본 URL을 그대로 fetch |
| 2 | 모바일 URL 변환 | `blog.naver.com/{id}/{no}` -> `m.blog.naver.com/{id}/{no}` 변환 후 재시도. JS 렌더링 없이 일부 공개 글 접근 가능 |
| 3 | PostView URL 변환 | `m.blog.naver.com/PostView.naver?blogId={id}&logNo={no}` 형태로 변환 |
| 4 | 사용자 붙여넣기 요청 | "네이버 블로그 본문을 가져오지 못했습니다. 본문을 직접 붙여넣어 주세요." |

**Playwright는 MVP에서 제외하는 이유:**
- Claude Code sandbox에서 headless Chromium 다운로드/실행이 sandbox 정책에 따라 차단될 수 있음 (검증되지 않은 가정)
- 네이버 rate limiting으로 IP 차단 위험
- 설치/설정 복잡성이 스킬의 "즉시 사용 가능" 원칙에 반함
- Phase 2에서 Playwright MCP 옵션으로 재검토

**플랫폼별 WebFetch 가능 여부:**

| 플랫폼 | 가능 여부 | 비고 |
|--------|----------|------|
| 티스토리 | 가능 | 일반 HTML, 단순 fetch로 본문 추출 |
| 브런치 | 부분적 | SSR 페이지, 일부 fetch 가능 |
| 네이버 블로그 | 제한적 | 모바일 URL 폴백 필요 |
| 일반 웹 | 가능 | WebFetch로 대부분 접근 가능 |

## 3. 프리셋 시스템

### 3.1 프리셋 목록 (5개 유지)

| # | ID | 이름 | 톤 | 구조 | 대상 글자 수 | 최적 플랫폼 |
|---|-----|------|-----|------|-------------|------------|
| 1 | `informative` | 정보전달형 | 객관적/~합니다 | H2/H3 계층, 리스트 활용 | 1,500-3,000 | 네이버, 티스토리 |
| 2 | `storytelling` | 스토리텔링형 | 친근/~해요 | 최소 헤딩, 짧은 문단 | 1,000-2,500 | 브런치 |
| 3 | `how-to` | 실용/가이드형 | 실용적/~해보세요 | 번호 단계, 팁/주의 박스 | 2,000-4,000 | 티스토리, 네이버 |
| 4 | `listicle` | 리스트/큐레이션형 | 경쾌/간결 | 번호 항목, 항목당 2-4문장 | 1,500-3,500 | 네이버 |
| 5 | `opinion` | 의견/분석형 | 확신/논리적 | 주장별 H2, 근거-반론 구조 | 2,000-3,500 | 브런치 |

**5개를 유지하는 이유:**
- 한국 블로그의 주요 유형을 거의 커버
- SEO 최적화는 별도 프리셋이 아닌 공통 레이어로 분리 (모든 글에 적용)
- 리뷰형은 `listicle` + `opinion` 조합 + 커스텀 옵션으로 대응 가능
- 프리셋 추가는 선택 피로도 증가 + 유지보수 비용 상승

**Phase 2 검토 대상:**
- `review` (리뷰형): 기존 코드(blog-writer.js)에 summaryBox, betterComment 등 리뷰 렌더링이 이미 구현되어 있어 실 사용례가 빈번함을 확인. v2에서 독립 프리셋으로 승격 검토.

### 3.2 동적 선택 로직

기존: 사용자에게 번호 선택 요청, 스킵 시 토픽 유형 기반 자동 추천.

개선: 2단계 분석으로 정확도 향상 + 추천 이유 명시.

```
[동적 선택 흐름]

입력 분석 결과 (토픽, 키워드, 모드)
    │
    ├── 1차: 규칙 기반 매칭 (기존 유지)
    │   기술/도구 → informative / how-to
    │   경험담/일상 → storytelling
    │   비교/추천/목록 → listicle
    │   뉴스/트렌드/분석 → opinion
    │
    ├── 2차: 입력 텍스트 신호 분석 (신규)
    │   "~하는 방법" / "~하는 법" → how-to
    │   "TOP" / "N가지" / "추천" / "모음" → listicle
    │   "왜" / "~해야 하는 이유" / "~의 문제" → opinion
    │   URL 입력 + 원문이 에세이 → storytelling
    │   "설명" / "개념" / "정리" → informative
    │
    └── 최종: 추천 + 사용자 확인
        "이 주제에는 [how-to] 스타일을 추천합니다.
         (이유: '~하는 방법' 패턴이 감지되었습니다)
         다른 스타일을 원하시면 번호를 선택하세요:
         1. 정보전달형  2. 스토리텔링형  3. 실용/가이드형
         4. 리스트형  5. 의견/분석형  6. 커스텀"
```

**핵심 원칙:**
- 항상 추천하되, 항상 오버라이드 가능
- 추천 이유를 한 줄로 명시 (사용자 신뢰 확보)
- LLM에게 매번 새 프리셋을 "생성"시키지 않음 -- 5개 프리셋의 파라미터 조합이 더 예측 가능하고 비용 효율적

### 3.3 커스텀 옵션 (6번 선택 시)

기존: 톤, 대상, 길이, 구조 선호도를 개방형 질문으로 수집.

개선: 기존 프리셋 파라미터를 조합하는 방식으로 구조화.

```
커스텀 스타일 설정:
1. 기본 톤: [formal/informal/mixed] (기본값: mixed)
2. 문장 종결: [~합니다/~해요/~이다] (기본값: ~합니다)
3. 문단 길이: [짧은2-3/보통3-5/긴4-6] (기본값: 보통)
4. 구조: [계층형/순서형/자유형] (기본값: 계층형)
5. 대상 길이: [short 1000/medium 2000/long 3500] (기본값: medium)
```

## 4. SEO 공통 레이어

모든 프리셋에 공통 적용되는 SEO 규칙. 기존에는 프리셋별로 개별 기술되어 있던 것을 분리.

**seo-layer.md에 포함할 내용:**

| 항목 | 규칙 |
|------|------|
| 제목 | 핵심 키워드를 제목 앞부분에 배치, 30자 이내 |
| 첫 문단 | 핵심 키워드를 자연스럽게 포함 |
| H2 헤딩 | 최소 1개 H2에 키워드 포함 |
| 키워드 밀도 | 본문에 키워드 3-5회 자연스럽게 분포 |
| 메타 설명 | 50-80자, 키워드 포함, 클릭 유도 |
| 내부 링크 | 관련 주제 언급 시 링크 유도 문구 |
| 이미지 ALT | 이미지 삽입 위치 표시 시 ALT 텍스트 포함 |

**네이버 특화 SEO (naver-optimization.md):**
- 네이버 블로그 C-Rank / DIA 로직 고려
- 본문 1,500자 이상 권장
- 이미지 3장 이상 삽입 위치 표시
- 태그/카테고리 제안

## 5. 온보딩 흐름

### 5.1 설계 원칙

**"API 키가 없어도 핵심 기능은 모두 동작한다"**

- Claude Code의 WebSearch/WebFetch는 API 키 없이 사용 가능
- 네이버 Open API는 검색 품질을 강화하는 선택 사항
- 온보딩은 최소화하되, 있으면 좋은 것은 안내

### 5.2 온보딩 플로우

```
[스킬 첫 실행]
    │
    ├── config 파일 확인: ~/.blog-writer/config.json
    │
    ├── 존재하면 → 설정 로드 → Step 1로 진행
    │
    └── 없으면 → 온보딩 시작
         │
         ├── 1. 선호 플랫폼 (선택)
         │   "주로 어떤 플랫폼에 글을 쓰시나요?
         │    1. 네이버 블로그  2. 브런치  3. 티스토리  4. 기타/상관없음"
         │   → 프리셋 자동 추천에 활용
         │
         ├── 2. 네이버 API 키 (선택)
         │   "네이버 검색 API를 연결하면 더 정확한 리서치가 가능합니다.
         │    (없어도 기본 웹 검색으로 동작합니다)
         │    설정하시겠어요? (y/n)"
         │   → y: developers.naver.com 발급 안내 + 키 입력
         │   → n: WebSearch fallback
         │
         └── 3. config 저장
             ~/.blog-writer/config.json 에 설정 저장
             다음 실행부터 자동 적용
```

### 5.3 API 키 목록

| 키 | 용도 | 발급처 | 필수 여부 |
|---|---|---|---|
| `NAVER_CLIENT_ID` | 네이버 Search API (블로그/카페 검색) | developers.naver.com | 선택 |
| `NAVER_CLIENT_SECRET` | 위와 동일 | developers.naver.com | 선택 |
| `NAVER_SEARCHAD_CUSTOMER_ID` | 키워드 검색량 조회 | searchad.naver.com | 선택 |
| `NAVER_SEARCHAD_ACCESS_LICENSE` | 위와 동일 | searchad.naver.com | 선택 |
| `NAVER_SEARCHAD_SECRET_KEY` | 위와 동일 | searchad.naver.com | 선택 |

스킬 방식에서는 `ANTHROPIC_API_KEY`가 불필요 (Claude Code가 직접 처리).

### 5.4 에러 핸들링

| 상황 | 대응 |
|------|------|
| API 키 없음 | graceful skip + "WebSearch로 검색합니다" 안내 |
| API 키 오류 (401/403) | "네이버 API 키가 유효하지 않습니다. 재발급이 필요합니다." + 링크 |
| Rate limit (429) | 3회 자동 재시도 (기존 서버 코드 패턴 참조) → 실패 시 WebSearch fallback |
| WebFetch 실패 | 네이버 URL이면 모바일 URL 변환 → 재실패 시 붙여넣기 요청 |

## 6. 기존 코드 재사용 항목

기존 서버(server.js, blog-writer.js, style-memory.js, agent.js)와 새 스킬은 **독립적으로 설계**한다.
단, 아래 패턴과 로직은 참조/재현 가치가 있다.

| 기존 코드 | 위치 | 재사용 방법 |

| 네이버 Search API 호출 로직 | `server.js: fetchNaverSource()` | 네이버 API 키 설정 시 동일 패턴으로 Bash 스크립트에서 호출 |

## 7. 구현 단계별 계획

### Phase 1: MVP (기존 스킬 개선)

**목표:** 현재 blog-writer 스킬을 실용적으로 개선. API 키 없이 완전히 동작.

**작업 항목:**

| # | 작업 | 파일 | 설명 |
|---|------|------|------|
| 1-1 | SKILL.md 개선 | SKILL.md | Step 0(온보딩) 추가, Step 2 리서치 서브에이전트 위임 지시, Step 3 동적 추천 강화 (텍스트 신호 분석), 네이버 URL 폴백 로직 추가 |
| 1-2 | SEO 공통 레이어 | references/seo-layer.md | 신규 파일 작성: 키워드 배치, 메타 설명, 제목 최적화 규칙 |
| 1-3 | 네이버 최적화 가이드 | references/naver-optimization.md | 신규 파일 작성: 네이버 SEO, URL 변환 패턴, 본문 요건 |
| 1-4 | style-presets.md 정리 | references/style-presets.md | SEO 관련 항목을 seo-layer.md로 이동, 커스텀 옵션 구조화 |
| 1-5 | 온보딩 흐름 구현 | SKILL.md + config 구조 | 첫 실행 감지 + 플랫폼/API 키 설정 안내 |

**MVP 완료 기준:**
- `/blog-writer 주제` 로 호출하면 리서치->프리셋 추천->블로그 생성 완료
- 네이버 블로그 URL 입력 시 모바일 URL 폴백 시도
- API 키 없이 WebSearch/WebFetch만으로 동작
- SEO 규칙이 모든 프리셋에 공통 적용

## 8. 핵심 설계 결정 요약

| # | 결정 | 근거 |
|---|------|------|
| 1 | **스킬 방식 채택** | 선형 파이프라인, 기존 구조 존재, UX 최적 (전원 동의) |
| 2 | **프리셋 5개 유지** | 주요 유형 커버 충분, 추가 시 선택 피로도/유지보수 비용 증가 |
| 3 | **동적 선택 = 규칙 기반 추천 + 사용자 확인** | LLM 동적 생성은 비용 대비 효과 낮음, 예측 가능한 규칙이 우선 |
| 4 | **리서치를 서브에이전트로 위임** | 메인 컨텍스트 윈도우 보호 (WebSearch/WebFetch 결과가 크므로) |
| 5 | **SEO는 공통 레이어** | 프리셋별 중복 제거, 모든 글에 일관된 SEO 적용 |
| 6 | **네이버는 계층적 폴백** | Playwright는 검증 안 됨, 모바일 URL이 현실적 대안 |
| 7 | **온보딩 최소화** | API 키 없이 핵심 기능 동작이 원칙, 네이버 API는 선택 사항 |
| 8 | **기존 서버와 독립** | 기존 서버는 ChatGPT Puppeteer 방식, 의존성 복잡화 방지 |
